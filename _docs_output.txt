10. Troubleshooting
WSL shows To Godot: 0
 
WSL shows Processed: 0
This usually means the pose landmark keys are integers but the code expects strings. This was a known bug that was fixed — make sure you have the latest version of the zip file.
 
MediaPipe skeleton disappears when moving fast
Lower min_tracking_confidence in config/settings.json to 0.2
Improve your lighting — face a window or lamp
Make sure your full upper body is visible in frame
Move slightly slower — MediaPipe struggles with motion blur
 
Mannequin arms look twisted or backwards
This is a coordinate system mismatch. Make sure you are using the latest version of mapper.py from the zip file which includes the mediapipe_to_godot coordinate conversion.
 
Godot says Bone not found
Your Y-Bot import may have different bone name formatting. Check the Output panel when Godot starts — it prints all bone names. The script expects names like mixamorig_RightArm (underscore, not colon). If your import uses different names, update the BONE_MAP dictionary in the Godot script.
 
Camera not found
Open config/settings.json and try changing camera_id to 1 or 2. Some systems have virtual cameras registered as device 0.
 
python3-venv not available in WSL
 
sudo apt update
sudo apt install -y python3-full
# If that fails:
pip3 install --user --break-system-packages virtualenv
python3 -m virtualenv venv_wsl

1. System Overview
This guide covers setting up the full dual-pipeline motion capture system from scratch. The system uses two separate tracking engines running in parallel — RTMPose for body and arm tracking on GPU, and MediaPipe Holistic for detailed hand and finger tracking on CPU. Both streams are composited into one display and merged before sending to Godot Engine for 3D avatar visualization.

Architecture summary:
Windows side: Camera capture, RTMPose (GPU), MediaPipe Hands (CPU), dual pipeline merge, UDP sender
WSL side: Coordinate normalization, bone transform calculation, UDP forwarder to Godot
Godot Engine: 3D avatar visualization, receives bone data via UDP port 8888

2. System Requirements
2.1 Hardware
NVIDIA GPU (GTX 1660 or better recommended, RTX series preferred)
8GB RAM minimum, 16GB+ recommended
Webcam (built-in or USB)
Windows 10/11 with WSL2 enabled

2.2 Software to Install
Install all of the following before proceeding. Links are provided in order.


3. CUDA Setup — Critical Step
RTMPose requires CUDA 12 runtime DLLs to run on GPU. Without this step the model falls back to CPU and runs at 2-3 FPS instead of 30+ FPS. Follow these steps exactly.

3.1 Add CUDA to System PATH (Run PowerShell as Administrator)
Right-click the Start menu, select 'Windows PowerShell (Admin)' or 'Terminal (Admin)', then run:

[System.Environment]::SetEnvironmentVariable("PATH", $env:PATH + ";C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v12.6\bin", [System.EnvironmentVariableTarget]::Machine)

NOTE: If you get 'access denied', make sure you opened PowerShell as Administrator (right-click → Run as administrator).

3.2 Verify CUDA DLLs are findable
Close and reopen PowerShell (normal, not admin), then run:
where cudart64_12.dll
It should print the path to the CUDA bin folder. If it shows nothing, restart your PC and try again.

3.3 Verify GPU is accessible to Python
python -c "import onnxruntime as ort; print(ort.get_available_providers())"
You should see CUDAExecutionProvider in the list. If not, check that cuDNN was installed correctly.

5. Full GDScript — Copy This Exactly
This is the complete script. Copy every line including the blank lines. Indentation uses tabs not spaces — make sure your editor does not convert tabs to spaces.

extends Node3D
 
var udp := PacketPeerUDP.new()
const PORT := 8888
 
var skeleton: Skeleton3D = null
var packets_received := 0
var last_frame_id := 0
 
const SCALE := 2.0
 
var rest_angles: Dictionary = {}
 
 
func _ready() -> void:
    print("=".repeat(60))
    print("KHMER SIGN RECOGNIZER - GODOT VISUALIZATION")
    print("=".repeat(60))
    skeleton = _find_skeleton(self)
    if skeleton == null:
        push_error("No Skeleton3D found!")
        return
    print("Skeleton found: ", skeleton.get_path())
    _cache_rest_angles()
    var err := udp.bind(PORT)
    if err == OK:
        print("UDP listening on port ", PORT)
    else:
        push_error("UDP bind failed")
    print("=".repeat(60))
 
 
func _cache_rest_angles() -> void:
    var arm_bones = [
        "mixamorig_LeftArm", "mixamorig_RightArm",
        "mixamorig_LeftForeArm", "mixamorig_RightForeArm"
    ]
    for bone_name in arm_bones:
        var bone_idx := skeleton.find_bone(bone_name)
        if bone_idx == -1:
            continue
        var global_basis := Basis.IDENTITY
        var idx := bone_idx
        var chain: Array = []
        while idx != -1:
            chain.push_front(idx)
            idx = skeleton.get_bone_parent(idx)
        for cidx in chain:
            global_basis = global_basis * skeleton.get_bone_rest(cidx).basis
        var world_dir := global_basis.y.normalized()
        rest_angles[bone_name] = atan2(world_dir.x, world_dir.y)
 
 
func _process(_delta: float) -> void:
    while udp.get_available_packet_count() > 0:
        var raw  := udp.get_packet()
        var text := raw.get_string_from_utf8()
        var json := JSON.new()
        if json.parse(text) == OK:
            _apply_bone_data(json.get_data())
            packets_received += 1
            if packets_received % 120 == 0:
                print("packets: %d | frame %d" % [packets_received, last_frame_id])
 
 
func _apply_bone_data(data: Dictionary) -> void:
    if data.has("frame_id"):
        last_frame_id = data["frame_id"]
    if skeleton == null:
        return
    var bones: Dictionary = data.get("bone_transforms", {})
    if bones.is_empty():
        return
    var l_shoulder := _get_pos(bones, "pos_left_shoulder")
    var r_shoulder := _get_pos(bones, "pos_right_shoulder")
    var l_elbow    := _get_pos(bones, "pos_left_elbow")
    var r_elbow    := _get_pos(bones, "pos_right_elbow")
    var l_wrist    := _get_pos(bones, "pos_left_wrist")
    var r_wrist    := _get_pos(bones, "pos_right_wrist")
    if l_shoulder != null and l_elbow != null:
        _point_bone("mixamorig_LeftArm", l_shoulder, l_elbow)
    if l_elbow != null and l_wrist != null:
        _point_bone("mixamorig_LeftForeArm", l_elbow, l_wrist)
    if r_shoulder != null and r_elbow != null:
        _point_bone("mixamorig_RightArm", r_shoulder, r_elbow)
    if r_elbow != null and r_wrist != null:
        _point_bone("mixamorig_RightForeArm", r_elbow, r_wrist)
    if data.has("finger_transforms"):
        var fingers: Dictionary = data["finger_transforms"]
        for finger_key in fingers.keys():
            var fd: Dictionary    = fingers[finger_key]
            var bone_name: String = fd["bone_name"]
            var rot_arr: Array    = fd["rotation"]
            var q := Quaternion(rot_arr[0], rot_arr[1], rot_arr[2], rot_arr[3])
            q = q.normalized()
            _apply_finger_rotation(bone_name, q)
 
 
func _get_pos(bones: Dictionary, key: String) -> Vector3:
    if not bones.has(key):
        return Vector3.ZERO
    var p: Dictionary = bones[key]
    return Vector3(-p["x"] * SCALE, -p["y"] * SCALE, 0.0)
 
 
func _point_bone(bone_name: String, from_pos: Vector3, to_pos: Vector3) -> void:
    var bone_idx := skeleton.find_bone(bone_name)
    if bone_idx == -1:
        return
    var dir := (to_pos - from_pos)
    dir.z = 0.0
    if dir.length() < 0.001:
        return
    dir = dir.normalized()
    var target_angle: float = atan2(dir.x, dir.y)
    var rest_angle: float   = float(rest_angles.get(bone_name, 0.0))
    var delta_angle: float  = -(target_angle - rest_angle)
    var q    := Quaternion(Vector3(0, 0, 1), delta_angle)
    var rest := skeleton.get_bone_rest(bone_idx)
    var new_pose := rest
    new_pose.basis = Basis(q) * rest.basis
    skeleton.set_bone_pose(bone_idx, new_pose)
 
 
func _apply_finger_rotation(bone_name: String, q: Quaternion) -> void:
    var bone_idx := skeleton.find_bone(bone_name)
    if bone_idx == -1:
        return
    var rest     := skeleton.get_bone_rest(bone_idx)
    var new_pose := rest
    new_pose.basis = Basis(q) * rest.basis
    skeleton.set_bone_pose(bone_idx, new_pose)
 
 
func _find_skeleton(node: Node) -> Skeleton3D:
    if node is Skeleton3D:
        return node
    for child in node.get_children():
        var result := _find_skeleton(child)
        if result != null:
            return result
    return null

6. How the Script Works
6.1 _cache_rest_angles()
This function runs once at startup and walks the full bone chain from the skeleton root to each arm bone. It accumulates the world-space rotation of each bone by multiplying all the parent rest poses together. The result tells us the true resting direction of each arm bone in world space — for this Y-Bot the left arm rests at +90 degrees (pointing right) and the right arm at -90 degrees (pointing left) in the XY plane.
Without caching these angles, every rotation calculation would be wrong because Mixamo bakes a 90-degree offset into the bone hierarchy that we have to compensate for.

6.2 _get_pos()
Converts the joint positions sent from WSL into Godot world space. WSL sends normalized coordinates where X increases toward the subject's left side and Y increases downward (pixel coordinate convention). Godot uses X increasing right and Y increasing upward. The function flips both axes and scales by SCALE (default 2.0) to make the movement range visible in the 3D viewport.

6.3 _point_bone()
This is the core rotation function. It calculates a 2D angle in the XY plane from the joint position to the next joint position, then computes the delta between that angle and the bone's cached rest angle. This delta is applied as a rotation around the Z axis only. By constraining rotation to Z axis only we prevent the arms from bending forward or backward into the screen, which was the main bug from not having real depth data from a 2D camera.

6.4 _apply_finger_rotation()
Fingers use a different approach from arms because finger data comes from MediaPipe as quaternions (rotations) not as positions. The quaternion is applied directly on top of the bone rest pose. This works well for fingers because MediaPipe's hand landmark model produces reliable 3D finger orientations.

AI Training Workflow
Khmer Sign Language Recognition — Multi-Modal Training Pipeline
                                                 |  Version 2.0  |  March 2026

1. Overview and Research Context
This document describes the complete AI training pipeline for the Khmer Sign Language (KSL) recognition system. The approach is novel in that it uses a 3D mannequin preprocessing step — real video is converted to a standardized grey avatar before the AI processes it. This removes background noise, lighting variation, and person-to-person differences, which is the main challenge for sign language recognition in low-resource languages like Khmer.

The training uses three streams of data simultaneously — skeleton sequences from the capture pipeline, raw video landmarks as a secondary signal, and text descriptions from a vision-language model (DeepSeek-VL2) reading a Khmer sign language dictionary. This multi-modal approach compensates for the almost complete lack of existing labeled Khmer sign language datasets.

NOTE: Khmer sign language has almost no publicly available labeled dataset as of early 2026. The closest existing work is by Ponleur Veng at IDRI Cambodia (2024) with 2,645 sign videos. Our system must function with far less data, which is why multi-modal training is essential.

2. What the AI Needs to Learn
The goal is a model that takes a sequence of skeleton joint positions (60 frames) and outputs a predicted Khmer sign word. The input is not video — it is normalized 3D joint coordinates from our pipeline.

Input shape: 60 frames x 48 joints x 3 coordinates = (60, 48, 3) tensor per sequence.
The 48 joints break down as follows:
6 body joints: left/right shoulder, elbow, wrist
21 left hand joints: MediaPipe hand landmarks 0-20
21 right hand joints: MediaPipe hand landmarks 0-20

Output: probability distribution over the sign vocabulary (50-100 signs initially).

3. Three-Stream Training Architecture
The model is trained with three separate data streams that all point to the same label. This is called multi-modal contrastive learning and is the same core concept behind how OpenAI's CLIP model works. The advantage is the model builds a stronger internal representation of each sign because it learns from three different angles at once.

Stream 1 — Skeleton Sequences (Primary)
This is the main input. 60-frame windows of normalized joint positions recorded through the capture pipeline. Each sequence is labeled with the sign being performed. This is the only stream used at inference time — the other two are training-only.

Shape: (60, 48, 3) — frames x joints x xyz
Format: numpy .npy files, one per sequence
Label: integer index into vocabulary list

Stream 2 — DeepSeek-VL2 Dictionary Descriptions (Auxiliary Text)
A Khmer sign language dictionary contains illustrated images of each sign with the hand shape and movement described visually. DeepSeek-VL2 is a vision-language model that can read these images and generate text descriptions of what the hand is doing. These descriptions become text labels that the model learns to associate with the skeleton sequences.

Example: the dictionary image for the sign meaning 'hello' might produce the description 'right hand open palm facing forward, raised to head height, slight wave motion'. The model learns that sequences with that motion pattern correspond to that text description which corresponds to the sign label.

NOTE: DeepSeek-VL2-Tiny can run on an 8GB GPU. The full model requires 40GB+. Use the Tiny variant locally or call the API for the larger model.

KNOWN LIMITATION: DeepSeek-VL2 text descriptions of Khmer dictionary images may not always be accurate, especially for motion descriptions since the dictionary shows static images. The model must learn to bridge static illustration descriptions to dynamic movement sequences. This is an open research problem.
RESEARCH QUESTION: How can we generate better motion descriptions from static dictionary images? Is there a way to infer movement from the static pose illustration plus the written Khmer description?

Stream 3 — Raw Landmark Sequences (Secondary Video)
The same signing sessions filmed for Stream 1 also produce raw MediaPipe landmark coordinates before normalization. These are stored separately and used as a secondary training signal. The model sees both the normalized version (Stream 1) and the raw version (Stream 3) of the same sign, which forces it to learn sign identity that is robust to different body sizes and camera distances.

KNOWN LIMITATION: Stream 3 coordinates are NOT person-agnostic. A tall person produces different raw coordinates than a short person for the same sign. The model may overfit to signer-specific features if Stream 3 is weighted too heavily during training.
RESEARCH QUESTION: What is the optimal weighting between Stream 1 (normalized) and Stream 3 (raw) during training? Should the weighting be adaptive based on how much variation exists in the training set?

4.2 Recording procedure

4.3 Data augmentation
Since Khmer sign data is scarce, augmentation is critical. The following augmentations are applied automatically during training to multiply the effective dataset size without filming anything new.
Random scale: multiply all joint positions by 0.85 to 1.15
Random horizontal flip: mirror the entire sequence left-right (simulates left-handed signer)
Time warping: randomly stretch or compress sequences between 45 and 75 frames then resample to 60
Gaussian noise: add small random noise to joint positions (sigma=0.01)
Random rotation: rotate all joints by -15 to +15 degrees around Z axis

KNOWN LIMITATION: Horizontal flip augmentation assumes the sign is symmetric or that both left-handed and right-handed variants are valid for training. For signs that are strictly one-handed this may introduce incorrect samples. A per-sign flip flag should be maintained in the vocabulary list.
RESEARCH QUESTION: How do we automatically detect which signs are flip-safe versus directionally asymmetric? Can the model itself learn this distinction, or must it be manually annotated?

5. Model Architecture
5.1 Recommended: Transformer Encoder
A Transformer encoder with positional encoding is the recommended model. It was the architecture used in the 1st place solution for Google's isolated sign language recognition competition (GISLR 2023) with landmark input identical to ours.

Input: (batch, 60, 144)  — flatten 48 joints x 3 coords
Positional encoding: learned, length 60
Encoder layers: 4 layers, 8 attention heads, hidden dim 256
Pooling: mean across time dimension
Output: Linear(256, vocab_size) + Softmax

NOTE: Total parameters: approximately 2.1M. Trains in under 30 minutes on Google Colab T4 GPU for a 50-sign vocabulary.

5.2 Baseline: LSTM
If Transformer is too complex to implement first, start with a 2-layer bidirectional LSTM as baseline.
Input: (batch, 60, 144)
BiLSTM: 2 layers, hidden size 256, dropout 0.3
Pooling: last hidden state
Output: Linear(512, vocab_size) + Softmax

KNOWN LIMITATION: LSTM requires more training data than Transformer to reach equivalent accuracy. With fewer than 1000 sequences the LSTM tends to overfit and the Transformer generalizes better. This is a known limitation of the LSTM architecture on small sequence datasets.
RESEARCH QUESTION: Is there a hybrid architecture — LSTM for temporal patterns with attention for cross-frame dependencies — that outperforms both on very small Khmer datasets? This has not been tested for KSL specifically.

5.3 Advanced: Graph Convolutional Network (GCN)
GCN treats skeleton joints as a graph where edges represent bone connections. It is the highest-accuracy approach in published literature but also the most complex to implement. Recommended as a second iteration after the Transformer baseline is working.

KNOWN LIMITATION: Standard GCN implementations assume a fixed skeleton graph (25 or 33 nodes). Our skeleton has 48 joints with a non-standard topology combining RTMPose body joints and MediaPipe hand joints. The graph adjacency matrix must be manually defined to connect these two different skeleton formats correctly.
RESEARCH QUESTION: What is the optimal graph structure for combining RTMPose body joints (6 nodes) with MediaPipe hand joints (42 nodes)? Should the wrist joint serve as the bridge node between body and hand graphs, or should a learned adjacency matrix be used?

import numpy as np
import json, os, time, socket
from pathlib import Path

SEQUENCE_LENGTH = 60  # frames per sequence
DATA_DIR = Path('data/sequences')
DATA_DIR.mkdir(parents=True, exist_ok=True)

def collect_sequence(label: str, udp_port: int = 9998):
    """Listen on UDP for processed landmark data and save a sequence"""
    sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
    sock.bind(('0.0.0.0', udp_port))
    sock.settimeout(5.0)

    frames = []
    print(f'Recording {label}... press ENTER when ready')
    input()
    print('Recording started — perform the sign now')

    while len(frames) < SEQUENCE_LENGTH:
        try:
            data, _ = sock.recvfrom(65535)
            msg = json.loads(data.decode())
            frame_vec = extract_frame_vector(msg)
            if frame_vec is not None:
                frames.append(frame_vec)
                print(f'  Frame {len(frames)}/{SEQUENCE_LENGTH}', end='\r')
        except socket.timeout:
            print('Timeout waiting for data')
            break

    sock.close()
    if len(frames) == SEQUENCE_LENGTH:
        seq = np.array(frames, dtype=np.float32)  # (60, 144)
        label_dir = DATA_DIR / label
        label_dir.mkdir(exist_ok=True)
        fname = label_dir / f'{label}_{int(time.time())}.npy'
        np.save(fname, seq)
        print(f'Saved: {fname}')
    else:
        print(f'Incomplete sequence: only {len(frames)} frames')

def extract_frame_vector(msg: dict) -> np.ndarray:
    """Flatten all joint positions into a 1D vector (144 values)"""
    pose = msg.get('normalized_pose', {})
    lh   = msg.get('left_hand', {})
    rh   = msg.get('right_hand', {})
    vec  = []
    joint_order = ['left_shoulder','right_shoulder','left_elbow',
                   'right_elbow','left_wrist','right_wrist']
    for j in joint_order:
        if j in pose:
            vec.extend([pose[j]['x'], pose[j]['y'], pose[j]['z']])
        else:
            vec.extend([0.0, 0.0, 0.0])
    for hand in [lh, rh]:
        for i in range(21):
            lm = hand.get(str(i), {})
            vec.extend([lm.get('x',0), lm.get('y',0), lm.get('z',0)])
    return np.array(vec, dtype=np.float32) if len(vec) == 144 else None

if __name__ == '__main__':
    label = input('Enter sign label: ').strip().lower()
    collect_sequence(label)

# Cell 3 — Transformer model
import torch.nn as nn

class SignTransformer(nn.Module):
    def __init__(self, input_dim=144, num_classes=50, d_model=256, nhead=8, num_layers=4):
        super().__init__()
        self.input_proj = nn.Linear(input_dim, d_model)
        self.pos_enc = nn.Embedding(60, d_model)
        encoder_layer = nn.TransformerEncoderLayer(d_model, nhead, dim_feedforward=512,
                                                    dropout=0.1, batch_first=True)
        self.transformer = nn.TransformerEncoder(encoder_layer, num_layers)
        self.classifier = nn.Linear(d_model, num_classes)

    def forward(self, x):
        # x: (batch, 60, 144)
        positions = torch.arange(x.size(1), device=x.device).unsqueeze(0)
        x = self.input_proj(x) + self.pos_enc(positions)
        x = self.transformer(x)
        x = x.mean(dim=1)  # pool over time
        return self.classifier(x)

# Cell 4 — Train
from torch.utils.data import DataLoader, TensorDataset, random_split
from torch.optim import AdamW

device = 'cuda' if torch.cuda.is_available() else 'cpu'
print('Training on:', device)

X_t = torch.FloatTensor(X)
y_t = torch.LongTensor(y)
dataset = TensorDataset(X_t, y_t)
train_size = int(0.8 * len(dataset))
train_set, val_set = random_split(dataset, [train_size, len(dataset)-train_size])

8. Known Limitations and Open Research Questions
This section documents the known limitations of the current training approach. These are real engineering and research problems that need creative solutions — they are not trivially fixable by running more training epochs or collecting more data.

8.1 Temporal boundary problem
KNOWN LIMITATION: The system currently uses a fixed 60-frame sliding window with no detection of when a sign starts or ends. In real continuous signing, signs blend into each other with transitional movements between them. The model has no way to identify where one sign ends and the next begins.
RESEARCH QUESTION: How do we implement sign segmentation — detecting the boundary between signs — without adding a separate boundary annotation to every training sequence? Can an unsupervised method detect natural pause points in the skeleton movement velocity?

8.2 Signer independence vs. signer-specific features
KNOWN LIMITATION: The shoulder-width normalization makes sequences partially person-agnostic, but speed differences between signers are not normalized. A fast signer and a slow signer produce different temporal patterns for the same sign. The model may learn to recognize the specific signing speed of training signers rather than the sign itself.
RESEARCH QUESTION: How should signing speed be normalized across signers? Should sequences be time-warped to a canonical speed before training, and if so, what is the reference speed? Does time-warp augmentation fully compensate for speed variation or does it introduce artifacts?

8.3 Dictionary descriptions are static, signs are dynamic
KNOWN LIMITATION: DeepSeek-VL2 reads static dictionary illustrations and generates text descriptions. But signs are inherently temporal — the movement path matters as much as the hand shape. A static image description misses the motion component entirely. The text auxiliary signal from Stream 2 may actually mislead the model by associating static poses with dynamic movement patterns.
RESEARCH QUESTION: Is there a better source of motion descriptions for Khmer signs? Could we use the existing IDRI video dataset to generate motion descriptions using a video-language model instead of a static image model? What would the computational cost be?

8.4 Left hand vs right hand dominance
KNOWN LIMITATION: Khmer sign language, like all sign languages, has dominant and non-dominant hand conventions. The current pipeline treats both hands identically. For signs where only one hand is active, the idle hand produces noisy landmark data that may confuse the model.
RESEARCH QUESTION: Should we add a hand activity detection step that masks out the non-dominant hand when it is not actively signing? How do we distinguish between an idle hand and a hand that is part of a two-handed sign?

8.5 No continuous signing support
KNOWN LIMITATION: The current model is an isolated sign recognizer — it classifies one sign at a time from a clean 60-frame window. Real Khmer sign language sentences require recognizing connected signs with co-articulation effects where adjacent signs influence each other's hand shape.
RESEARCH QUESTION: What architecture changes are needed to extend from isolated sign recognition to continuous signing? Is a CTC (Connectionist Temporal Classification) loss function appropriate, or is attention-based sequence-to-sequence decoding better for Khmer sentence structure?
